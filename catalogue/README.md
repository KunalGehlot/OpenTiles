# Catalogue

The public catalogue lists **only verified public-domain or CC0 scores**, each with a provenance
record (spec §2, §9). Everything a user imports goes to their private library instead and never
appears here.

## Layout

```text
catalogue/
  index.json                 generated by tools/pipeline/build_index.py — do not edit
  REVIEWING.md               the 10-minute review checklist
  schema/provenance.schema.json
  cache/wikidata.json        death years from Wikidata, written by tools/pipeline/wikidata.py
  pieces/<slug>/
    provenance.json          required, see the schema
    score.musicxml           the score (or score.mxl)
    arrangement.txt          optional: source for arrangements written with arrange.py
```

## Adding a piece

1. Check the music is free in the EU: every composer (and lyricist, if there are lyrics) died in
   **1955 or earlier** for a 2026 release, or the tune is traditional.
2. Use a transcription that is the transcriber's own work under CC0, public domain or CC BY —
   never a scan or copy of a publisher's edition (scholarly and first editions have their own
   protection in Germany, §§ 70/71 UrhG). Say so in `edition_note` ("Own transcription …" or
   "Original arrangement …"). PDMX entries come only from its `no_license_conflict` subset.
3. Create `pieces/<slug>/` with the score and a `provenance.json` (copy an existing one).
   Leave `verified: false` and `reviewed_by: null`.
4. Look up the death years on Wikidata, rebuild the index and run the checks:

   ```sh
   python3 tools/pipeline/wikidata.py update      # needs the network; updates cache/wikidata.json
   python3 tools/pipeline/build_index.py
   python3 tools/pipeline/validate_catalogue.py
   ```

   If `wikidata.py` reports a name as ambiguous, set `composer_wikidata` (or
   `lyricist_wikidata`) to the right item ID, for example `"Q255"` for Beethoven.

5. Open a pull request with the **catalogue** template. CI rejects missing fields, composers
   inside the EU term, death years that disagree with Wikidata, missing edition evidence and
   scores that fail the musical checks.

### What the validator checks

`validate_catalogue.py` runs offline and checks, for every piece:

- the provenance record against the schema, including the EU term for composer and lyricist;
- the death years against the committed Wikidata cache (`--wikidata online` also looks up
  names missing from it);
- the edition rules of [`tools/pipeline/editions.py`](../tools/pipeline/editions.py): no
  publisher, Urtext, scholarly or first edition, no scan or music OCR, and an `edition_note`
  that states the transcriber's own work;
- the score: both hands have notes (or `single_hand` names the one hand), every pitch lies
  between A0 and C8, every note has a positive duration, and every bar matches its time
  signature (only an upbeat, the last bar or a bar marked `implicit` may be shorter);
- that `score.musicxml` matches `arrangement.txt`, and that `index.json` is current.

The web app's own test suite (`pnpm --filter @opentiles/song-model test`) also parses every
score into a `Song` and checks that it plays.

### Writing a simple arrangement

For beginner arrangements of public-domain tunes, write `arrangement.txt` in the compact notation
described at the top of [`tools/pipeline/arrange.py`](../tools/pipeline/arrange.py) and render it:

```sh
python3 tools/pipeline/arrange.py catalogue/pieces/<slug>/arrangement.txt > catalogue/pieces/<slug>/score.musicxml
```

Only arrange a melody you know exactly, and say in the first comment line where it comes from.
Your arrangement is released under CC0 1.0.

### Converting a typeset MIDI file

For public-domain piano pieces that someone else typeset and dedicated to the public domain (the
Mutopia Project lists the licence on each piece's page), `tools/pipeline/midi_arrange.py` turns the
MIDI file into an `arrangement.txt`:

```sh
python3 tools/pipeline/midi_arrange.py piece.mid --title "Invention No. 13" \
  --composer "Johann Sebastian Bach" --tempo 96 --comment "Source: ..." > arrangement.txt
python3 tools/pipeline/arrange.py arrangement.txt > score.musicxml
```

It writes one voice per hand, cuts a held note at the next onset and a note that crosses a barline
at the barline, and refuses triplets and finer rhythms (grace notes are dropped). Read the result
before committing it, say in the first comment line where the notes came from, and name the
typesetter in `transcriber`. Only use files whose licence is _Public Domain_ or CC0, never
CC BY-SA, which would not fit a CC0 catalogue. Leave `verified: false`.

### Finding pieces in PDMX

[PDMX](https://zenodo.org/records/15571083) is a set of about 254,000 public-domain and CC0
MusicXML scores. Download `PDMX.csv` from the dataset (about 225 MB; keep it out of git, for
example in `tools/pipeline/data/`) and filter it:

```sh
python3 tools/pipeline/pdmx_filter.py tools/pipeline/data/PDMX.csv --deduplicated
```

This keeps the `no_license_conflict` subset, piano-only scores and ratings of at least 4.0 from
at least three people, applies the edition rules and writes
`tools/pipeline/data/pdmx_candidates.csv` with complexity and size columns for difficulty
scoring. Run on the June 2025 release: 254,077 rows, 222,856 without a licence conflict,
181,141 piano-only, 4,255 rated 4.0 or more; the edition rules exclude 2 and mark 673 for review
(mostly files under a public-domain mark rather than a CC0 dedication). Every candidate still
needs the EU term check (`--term-check cache` or `online`), a file check and a human review.

The scores in PDMX are public domain or CC0, but the dataset as a compilation is CC BY 4.0
(Long et al., _PDMX: A Large-Scale Public Domain MusicXML Dataset for Symbolic Music
Processing_, 2024). Credit it in the release notes of any catalogue release that uses it.

## Reviewing a piece (about 10 minutes)

Follow [REVIEWING.md](REVIEWING.md). In short: a reviewer who did not add the piece checks the
rights (death years, licence, edition), listens to the piece in the app and compares it with a
public-domain source, checks the hand split, title, composer and difficulty, then sets
`verified: true`, `reviewed_by: "<GitHub handle>"` and `reviewed_on: "<YYYY-MM-DD>"`. Only
verified pieces appear in production builds.

recorded in its provenance file.

## Takedown

If you believe a piece is still protected, open an issue or use the contact in the Impressum.
Pieces are removed within 48 hours while the claim is checked.
